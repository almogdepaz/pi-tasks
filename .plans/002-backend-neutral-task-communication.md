# store/transport task communication layer

status: implemented
created: 2026-07-21

## goal

reframe `pi-tasks` from a wolfpack-specific delegation plugin into a store/transport-composed task communication layer for pi agents.

success state:
- task protocol/types are usable without wolfpack
- task store is generic and reusable
- pi tools compose a store + transport, not a monolithic adapter
- wolfpack dispatch is one transport implementation
- current wolfpack behavior remains compatible
- docs describe this as a communication layer, not a subagent spawner

## assumptions

1. the public tool names stay `agent_task_*` for now to preserve installed prompt/tool behavior.
2. wolfpack remains the default transport in this repo, but not the architectural center.
3. the first split should avoid publishing/package renames unless explicitly requested.
4. filesystem storage is generic shared task state; the default path should be `.pi/tasks`, not transport-owned storage.
5. dispatch is separate from storage: transports may deliver via wolfpack cli, http, local inbox polling, etc.
6. target sessions still complete through `agent_task_done`, independent of how assignments were delivered.

## proposed architecture

### 1. protocol package/module

owns stable contracts only:
- task ids
- statuses
- assignment envelope
- result payload
- task events
- artifact metadata
- compact result shape

no wolfpack naming in protocol types.

### 2. store and transport interfaces

an interface like:

```ts
interface TaskStore {
  createTask(input): Promise<CreateTaskResult>;
  getTask(taskId): Promise<TaskRecord>;
  getTaskResult(taskId): Promise<StoredTaskResult | undefined>;
  waitForTask(taskId, options): Promise<TaskRecord>;
  listInbox(parentSession, options): Promise<readonly TaskRecord[]>;
  ackTask(taskId, parentSession): Promise<TaskRecord>;
  cancelTask(taskId, reason): Promise<TaskRecord>;
  completeTask(taskId, status, payload): Promise<TaskRecord>;
}

interface TaskTransport {
  getCurrentSessionName(env): string;
  dispatchTask(task, assignment, signal): Promise<DispatchResult>;
}
```

pi tools depend on a composed `{ store, transport }` layer. most integrations only implement transport and reuse the filesystem store.

### 3. filesystem store

current store logic, generalized:
- configurable root dir
- no `.wolfpack` literal in generic code
- same locking/idempotency/event semantics
- task refs generated by store

### 4. wolfpack transport

wolfpack-specific code owns:
- session identity from env / future config
- target addressing string semantics
- `wolfpack session send <target> <assignment>`
- wolfpack-specific skill copy

### 5. pi extension composition

`src/extension.ts` should become thin:
- builds config
- constructs store + transport
- registers tools
- owns tui background notifications

### 6. docs/skills split

- readme: generic communication layer first
- docs: filesystem store, wolfpack transport
- skill: rename language away from “wolfpack only” where possible; keep wolfpack skill as adapter-specific guidance

## implementation steps

1. add tests that encode store/transport separation
   - protocol assignment envelope no longer says wolfpack except adapter wrapper tests
   - extension can be constructed around a fake store/transport pair
   - filesystem root defaults to `.pi/tasks` and remains configurable

2. extract generic protocol names
   - rename wolfpack assignment envelope type to generic task assignment v1
   - keep backward-compatible parsing/wording where necessary

3. introduce store/transport interfaces
   - add `src/task-communication.ts`
   - route tools through composed store + transport

4. move current store into filesystem store
   - `src/stores/filesystem.ts`
   - configurable root path
   - do not make wolfpack transport own or imply a storage path

5. add wolfpack transport
   - `src/transports/wolfpack.ts`
   - owns cli dispatch and session naming

6. thin out extension
   - tool registration uses store + transport facade
   - no direct store-function imports in extension except construction

7. update docs and skill
   - describe communication layer positioning
   - list existing subagent plugins as adjacent, not competitors
   - document store/transport contracts for future adapters

8. verification
   - `bun test`
   - `bun run typecheck`

## non-goals for first split

- no server implementation
- no new wolfpack api
- no remote http store/transport unless requested after the split
- no package rename yet
- no changing user-facing tool names yet
- no terminal output polling

## decisions

1. assignment envelope changed to `pi.task.assignment.v1`.
2. generic filesystem storage defaults to `.pi/tasks`; wolfpack is transport-only and does not own storage.
3. composition is internal factory-based for v1: default extension uses generic filesystem store + wolfpack transport, and downstream packages can call `registerAgentTaskTools` with another store/transport pair.
